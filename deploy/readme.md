# Выкладка VNL на сервер

Здесь лежит всё, чем приложение разворачивается: образ, служба, прокси. Две
дороги -- docker и systemd -- дают одинаковый результат: один процесс, который
слушает только loopback, и nginx перед ним, который выпускает его наружу под
TLS и паролем. Выбирать по тому, что уже стоит на машине.

| Файл | Зачем |
| --- | --- |
| `../Dockerfile` | образ: сборка интерфейса на node, запуск на python |
| `../.dockerignore` | что не едет в контекст сборки (в первую очередь `.vnl/`) |
| `compose.yml` | сервис, том под хранилище, порт на `127.0.0.1` |
| `vnl.service` | служба systemd для выкладки без docker |
| `install.sh` | установка без docker: пользователь, venv, сборка, служба |
| `nginx.conf.example` | обратный прокси: TLS, basic auth, правильный `Host` |

## Что важно знать до начала

**Один процесс, без исключений.** Симуляции считаются в фоновых потоках самого
процесса и живут в его памяти. Сессия, открытую одним процессом, второй не
увидит: пользователь нажмёт «пуск» и получит «нет такой симуляции». Поэтому ни
воркеров, ни реплик, ни `--scale` -- одна служба, один контейнер.

**Хранилище -- данные, а не код.** Библиотека это каталог с файлами:
`patterns/*.json`, `sandboxes/*.json`. Он живёт вне кода (`/var/lib/vnl` или том
docker) и выкладку новой версии переживает нетронутым. В образ он не попадает
никогда -- `.dockerignore` отсекает `.vnl/` отдельной строкой.

**Вход у приложения есть, но включается настройками.** Без переменных
`VNL_OIDC_*` и `VNL_SESSION_SECRET` сервер ведёт себя как раньше -- инструмент
на одного человека, закрытый тем, что слушает `127.0.0.1`. На стенде, где перед
ним стоит nginx, эти настройки обязательны: прокси ходит сюда с
`Host: localhost`, то есть проверка `Host` пропускает весь интернет, и без входа
любой смог бы `DELETE /api/patterns/<id>` и стереть библиотеку.

Что вход даёт и чего не даёт. Библиотека -- витрина: каталог, карточка и живая
симуляция паттерна открыты всем без учётной записи (#516), на схему дают ссылку.
Песочницы закрыты все до единой, включая чтение, и у каждой есть владелец
(#520): в списке человек видит свои и те, что завели до появления владельцев, --
последние остались общими и помечены `shared`. Чужая песочница отвечает тем же,
чем несуществующая. Правка библиотеки при этом доступна всем вошедшим: она общая
по замыслу, а не по недосмотру.

Пароль на прокси после этого не обязателен, но и не лишний -- подробности и
причины в комментариях `nginx.conf.example`.

## Дорога 1: docker

```bash
sudo git clone <репозиторий> /opt/vnl
cd /opt/vnl
sudo docker compose -f deploy/compose.yml up -d --build
curl -fsS http://127.0.0.1:8765/api/health
```

Ответ `/api/health` -- живые данные: версия, путь хранилища, сколько паттернов,
сколько открытых симуляций. Если пришёл JSON, приложение работает.

Обновление:

```bash
cd /opt/vnl && sudo git pull
sudo docker compose -f deploy/compose.yml up -d --build
```

Том `vnl-data` при этом не пересоздаётся, данные остаются. Старые образы
убираются `docker image prune`.

Что где внутри:

* хранилище -- том `vnl-data`, смонтирован в `/var/lib/vnl`;
* интерфейс -- `/app/ui/dist`, сервер отдаёт его сам;
* порт -- `127.0.0.1:8765` на хосте, наружу его выпускает nginx;
* корень контейнера смонтирован только для чтения, писать можно лишь в том.

### Почему в контейнере `--bind 0.0.0.0`

По умолчанию сервер привязывает сокет к `127.0.0.1` -- для инструмента на машине
пользователя это правильное значение. Внутри контейнера у этого адреса другой
смысл: это loopback самого контейнера, и опубликованный порт до него не доходит,
потому что docker соединяется с адресом контейнера. Процесс, который слушает
127.0.0.1 внутри контейнера, снаружи не отвечает вообще.

Поэтому команда образа запускает `vnl serve --bind 0.0.0.0`. Ограничение «только
с этой машины» никуда не девается: его держат docker (порт публикуется на
`127.0.0.1` хоста) и проверка заголовка `Host` в самом приложении -- она работает
при любом адресе. Отсюда же обязательный `proxy_set_header Host localhost;` в
nginx: без него будет 403.

В конце `compose.yml` описан и вариант с `network_mode: host` -- тогда флаг не
нужен вовсе, но контейнер делит сетевое пространство с хостом.

## Дорога 2: systemd, без docker

```bash
sudo git clone <репозиторий> /opt/vnl
sudo bash /opt/vnl/deploy/install.sh
```

(`bash` перед путём -- чтобы не зависеть от бита исполнения: он теряется при
переносе с Windows. Если в репозитории бит проставлен --
`git update-index --chmod=+x deploy/install.sh` -- скрипт запускается и напрямую.)

Скрипт делает: пользователя `vnl` (системный, без оболочки), `/var/lib/vnl` под
хранилище, venv в `/opt/vnl/.venv` с установленным пакетом, `npm ci && npm run
build` в `ui/`, юнит в `/etc/systemd/system/vnl.service`, запуск и проверку
`/api/health`. Нужны python3 >= 3.11, node с npm и systemd.

Каталоги можно сдвинуть переменными: `APP_DIR=/srv/vnl DATA_DIR=/srv/vnl-data
PORT=9000 sudo -E bash deploy/install.sh` -- пути подставятся и в юнит.

Обновление -- тот же скрипт:

```bash
cd /opt/vnl && sudo git pull && sudo bash deploy/install.sh
```

Он переустановит пакет, пересоберёт интерфейс и перезапустит службу. Хранилище не
трогается.

Полезное:

```bash
systemctl status vnl
journalctl -u vnl -f
sudo systemctl restart vnl
```

## Прокси

```bash
sudo cp deploy/nginx.conf.example /etc/nginx/sites-available/vnl
sudo $EDITOR /etc/nginx/sites-available/vnl        # домен и пути к сертификату
sudo apt-get install -y apache2-utils
sudo htpasswd -c /etc/nginx/vnl.htpasswd <имя>
sudo ln -s /etc/nginx/sites-available/vnl /etc/nginx/sites-enabled/vnl
sudo nginx -t && sudo systemctl reload nginx
```

Одна строка в этом конфиге важнее остальных:

```nginx
proxy_set_header Host localhost;
```

Приложение проверяет `Host` и пускает только `localhost`, `127.0.0.1`, `::1` --
это защита от обращения к локальному порту со страницы чужого сайта (DNS
rebinding). nginx по умолчанию передаёт наверх имя клиента (`vnl.example.com`),
приложение отвечает 403 на каждый запрос, и это выглядит как «прокси настроен, а
сайт не работает». Настоящее имя уезжает в `X-Forwarded-Host` и не теряется.

Сертификат:

```bash
sudo certbot certonly --webroot -w /var/www/certbot -d vnl.example.com
```

Фаервол: порт 8765 наружу открывать не нужно ни в каком виде -- к нему ходит
только nginx с той же машины. Открытыми должны быть 80 и 443.

## Как положить схемы в библиотеку

Библиотека наполняется командой `vnl add`: она читает `.vnl`-файл и кладёт в
хранилище паттерн вместе с демонстрационным запуском. Ключ `--root` должен
указывать на то самое хранилище, с которым работает сервер, иначе схема ляжет
рядом и в интерфейсе не появится.

Порты (`--port имя=ТОЧКА`) -- то, чем паттерн потом вставляется в другую схему.
Без них паттерн сохранится черновиком и так и будет помечен в каталоге.

systemd:

```bash
sudo -u vnl /opt/vnl/.venv/bin/vnl add examples/ffi.vnl \
    --root /var/lib/vnl \
    --name "Прямое торможение" \
    --level L2 \
    --port in=IN.soma --port out=E.soma
```

docker -- разовым контейнером на том же томе; каталог со схемами пробрасывается
только на чтение:

```bash
sudo docker compose -f deploy/compose.yml run --rm --no-deps \
    -v /opt/vnl/examples:/schemas:ro \
    app vnl add /schemas/ffi.vnl \
        --root /var/lib/vnl \
        --name "Прямое торможение" \
        --level L2 \
        --port in=IN.soma --port out=E.soma
```

Команда после имени сервиса заменяет команду образа целиком, поэтому сервер в
этом контейнере не поднимается. Порт наружу разовый контейнер не публикует (для
этого нужен отдельный `--service-ports`), так что работающему сервису он не
мешает.

Можно и через уже запущенный контейнер -- тогда файл заносится внутрь копией
(`exec` монтировать не умеет):

```bash
sudo docker cp examples/ffi.vnl vnl:/tmp/ffi.vnl
sudo docker compose -f deploy/compose.yml exec app \
    vnl add /tmp/ffi.vnl --root /var/lib/vnl --port in=IN.soma --port out=E.soma
```

Проверить, что схема дошла:

```bash
curl -fsS http://127.0.0.1:8765/api/catalog | head -40
```

Перезапуск после `vnl add` не нужен: сервер читает каталог с диска на каждый
запрос.

## Резервная копия

Всё состояние -- это каталог хранилища, и копируется он обычным архиватором.

systemd:

```bash
sudo tar czf vnl-$(date +%F).tar.gz -C /var/lib/vnl .
```

docker:

```bash
sudo docker run --rm -v vnl-data:/data -v "$PWD:/out" alpine \
    tar czf /out/vnl-$(date +%F).tar.gz -C /data .
```

Восстановление -- распаковка в тот же каталог при остановленной службе: файлы
пишутся атомарно, но копия, снятая посреди записи, всё равно неприятна.
